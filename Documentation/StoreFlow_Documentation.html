1. Introduction & Project Purpose

StoreFlow is a management system built for superstores and grocery stores. It replaces manual, paper-based (or scattered spreadsheet) processes with a single connected system that covers inventory, order taking, worker coordination, payments, and reporting — usable from a computer (web app) or a phone (mobile app).

The system is multi-tenant, meaning one deployment of StoreFlow can serve many separate businesses at the same time. Each business ("tenant") only ever sees its own data — its own items, orders, staff, and customers — even though everyone is using the same backend and database.

1.1 Who is it for?

  • Store Owners — who want to manage inventory, staff, and see sales reports without hiring a developer for every change.
  • Counter Staff — who take customer orders at the counter/till.
  • Store Workers — who physically collect items from the shelves to fulfill an order.
  • Super Admin (platform owner) — the person who runs StoreFlow itself as a service to multiple store businesses (i.e. the developer/business selling this system to multiple clients).

1.2 The Three Parts of the Project

PartWhat it isWho uses it
BackendA Laravel (PHP) REST API — the "brain" of the system. Stores all data and enforces all business rules and permissions.Not used directly by people — both the Web App and Mobile App talk to it.
Frontend (Web App)A React single-page application used from a browser on a desktop/laptop.Owners, Counter Staff, Store Workers, Super Admin.

Both the Web App and the Mobile App are just two different "front doors" to the exact same Backend API — so a feature added to the backend is instantly available to both, and data stays perfectly in sync between web and mobile.

2.4 Why these choices?

  • Laravel was chosen because it comes with authentication, database handling (migrations), file uploads, and job scheduling already built in — much faster to build a solid backend than writing everything from scratch.
  • React + React Native together mean the same team/skillset (JavaScript) builds both the web and mobile app, and a lot of logic (like how WhatsApp receipts are built, or how search works) is written almost identically in both places.
  • SQLite is only for local development — see Section 9 for the production database plan (MySQL).

3.2 Multi-Tenancy (Many Businesses, One System)

Every important table (items, categories, orders, customers, purchases, staff, etc.) has a hidden tenant_id column. Every database query is automatically filtered to the logged-in user's own tenant_id — this is enforced at the model level (a Laravel "Global Scope"), so it is not something a developer can accidentally forget to add to a new query. This means:

  • Business A can never see Business B's items, orders, or staff.
  • The Super Admin account is the only role that is not tied to one tenant — it can see the list of all registered businesses and suspend/reactivate them, but it cannot see any business's actual store data (items, orders, customers).

3.3 Real-Time Order Updates (Web) vs. Polling (Mobile)

When a Counter Staff member places a new order, the assigned Store Worker's pick-list screen needs to show it immediately.

  • On the Web App: Laravel Reverb (a WebSocket server) pushes the new order to the browser the instant it is created — no refresh or delay.
  • On the Mobile App: instead of a WebSocket connection, the app checks for new orders automatically every 6 seconds. This was a deliberate simplicity choice — it works reliably on any network and needs no extra mobile-specific real-time setup.

3.4 Worker Auto-Assignment (Load Balancing)

When a new order is placed, the backend automatically decides which Store Worker should collect it:

  1. Find all Store Workers who are currently free (no order currently assigned to them that is still "placed" or "picking").
  2. Among the free workers, pick the one who has been assigned the fewest orders overall (fair rotation).
  3. If no worker is free, the order is left unassigned ("queued") and is invisible to all workers.
  4. As soon as any worker finishes their current order (marks it "ready"), the system automatically looks for the oldest queued order and assigns it to that now-free worker.

6. Local Development Setup (Step by Step)

6.1 Requirements

  • PHP 8.3+ with Composer installed
  • Node.js (v18+) with npm
  • Expo Go app (for quick testing) or Android Studio (for a full emulator) — optional if only testing on a real phone
  • A code editor (VS Code)

6.2 Backend Setup

cd Backend
composer install
copy .env.example .env          (Windows)   /   cp .env.example .env   (Mac/Linux)
php artisan key:generate
php artisan migrate
php artisan serve

This starts the API at http://127.0.0.1:8000. For real-time order updates, also run Reverb in a second terminal:

php artisan reverb:start

6.3 Frontend (Web App) Setup

cd Frontend
npm install
npm run dev

This opens the web app at http://localhost:5173 (Vite's default port). Make sure the Backend server (Section 6.2) is running at the same time.

6.4 Mobile App Setup

cd Mobile
npm install
npx expo start

Then scan the QR code shown in the terminal using the Expo Go app on your phone (for quick testing), or press a to open an Android emulator.

Important: the phone and the computer running the Backend must be on the same Wi-Fi network. Inside the Mobile App's Settings → API Address screen, enter the computer's local network IP address (e.g. http://192.168.1.5:8000) instead of localhost — a phone cannot reach "localhost" on the computer.

8. Building & Distributing the Mobile App (EAS Build)

Because a phone app cannot simply be "opened in a browser" the way a website can, it must be built into an installable file. StoreFlow uses EAS (Expo Application Services) — Expo's own cloud build service — so no local Android Studio / Xcode installation is required to produce a real app file.

8.1 The Three Build Profiles (in eas.json)

ProfilePurposeOutput
developmentA build with extra developer tools attached, for active coding/debuggingDevelopment client app
previewA real, shareable test build to install directly on a phone (no app store needed).apk file — directly installable
productionThe final version meant to be published to the Play Store / App Store.aab (Android App Bundle) — Play Store format
Why "preview" builds an APK and "production" builds an AAB: An AAB cannot be installed directly on a phone — it can only be uploaded to the Play Store, which then generates the actual installable file per device. An APK, on the other hand, can be shared and installed directly (perfect for testing with the client before an official store release).

8.2 Typical Build & Test Cycle

cd Mobile
npx eas login
eas build --profile preview --platform android

Wait for the build to finish in the cloud (a link is printed in the terminal, and it's also visible on expo.dev). Download the .apk file to the phone and install it.

App icon / name changes require a new build. Editing app.json or replacing an icon image has no effect on an already-installed app — a new eas build must be run, and the old app must be fully uninstalled (not just overwritten) before installing the new one, since some Android launchers cache the old icon/name otherwise.

8.3 Key app.json Settings

FieldPurpose
nameThe app name shown under the icon and during install
slugA URL-safe internal identifier for the Expo project
iconThe app icon shown on iOS and older Android — must be a square PNG (1024×1024 recommended)
android.packageThe unique Android package ID (e.g. com.astutemint.storeflow) — cannot be changed once published to the Play Store
android.adaptiveIconThe modern Android icon system (foreground image + background color/image) — takes priority over the plain icon field on Android 8+

9. Hosting & Deployment Plan

Not yet implemented — documented here as the agreed plan for when the project is ready to go live.

9.1 Backend (Laravel API) Hosting

OptionNotes
VPS (e.g. DigitalOcean, Hostinger VPS, Contabo)Full control server. Needs manual setup of PHP, Composer, Nginx/Apache, and a process manager. Best long-term option, most flexible.
Managed Laravel hosting (e.g. Laravel Forge + any VPS provider)Forge handles server setup, SSL, deployments automatically — recommended if avoiding manual server administration.
Shared hosting with PHP/Composer supportCheapest option, but many shared hosts don't allow the background processes StoreFlow needs (queue worker, Reverb) — needs to be checked with the host first.

9.2 Database — Move from SQLite to MySQL

SQLite (a single file) is fine for development but is not recommended for a live, multi-tenant production system. The plan is to switch DB_CONNECTION in .env to mysql and provide real database host/username/password — Laravel's migrations run unchanged on MySQL, no application code changes needed.

9.3 Frontend (Web App) Hosting

  • Run npm run build to produce a static dist folder.
  • Host it either on the same server as the backend (served by Nginx/Apache as static files) or on a static-hosting service like Vercel or Netlify (free tier available, simplest option, automatic SSL/CDN).
  • The web app just needs one setting: the backend API's live URL.

9.4 Real-Time (Reverb) in Production

Laravel Reverb needs a long-running process (not just a normal web request) to keep WebSocket connections open. On a VPS this is managed with a process supervisor (e.g. Supervisor) running php artisan reverb:start permanently in the background. As a simpler alternative, a hosted WebSocket service (e.g. Pusher's cloud service, which Laravel already supports through the same Echo/Pusher-js libraries used in the frontend) can be used instead of self-hosting Reverb.

9.5 Domain & SSL

  • A domain name is pointed at the server (e.g. api.storeflow.com for the backend, app.storeflow.com for the web app).
  • Free SSL certificates (Let's Encrypt) are used so everything runs on https:// — required for the mobile app to connect reliably and for browsers to not show a security warning.

10. SMS & WhatsApp Messaging Solution

10.1 WhatsApp Receipts — Live Now

After a payment is processed, a green "Send Receipt" WhatsApp button appears next to the customer's name (on both web and mobile). Tapping it opens WhatsApp with the customer's number and a pre-written receipt message already filled in — the staff member just presses send.

Important limitation: this uses WhatsApp's free "click-to-chat" link (wa.me) — there is no way to check in advance whether a phone number is actually registered on WhatsApp. If it isn't, WhatsApp itself will show an error when the message is opened. There is no cost for this method, but it requires WhatsApp to be installed on the device sending the message, and a person still has to press "Send".

10.2 SMS Due-Payment Reminders — Code Complete, Needs Twilio Account

For customers who bought on credit ("due" payment) and haven't paid yet, StoreFlow can automatically send a real SMS reminder. This is fully coded and tested using Twilio, a paid SMS-sending service — it only needs a live Twilio account to actually start sending messages.

What is needed to go live:

  1. Create an account at twilio.com and add billing (SMS costs a small fee per message, varies by country).
  2. Get a Twilio phone number that can send SMS to the target country.
  3. Copy three values from the Twilio dashboard: Account SID, Auth Token, and the Twilio phone number.
  4. Add them to the Backend's .env file: 
    TWILIO_SID=your-account-sid
TWILIO_AUTH_TOKEN=your-auth-token
TWILIO_FROM_NUMBER=+1xxxxxxxxxx
TWILIO_DEFAULT_COUNTRY_CODE=+92
  5. Run php artisan reminders:send-due once manually to confirm a real SMS arrives, then it runs automatically once a day on its own schedule going forward.

10.3 Future Option — Official WhatsApp Business API

If more reliable, fully-automated WhatsApp sending is wanted later (instead of the manual click-to-send method above), the official WhatsApp Business Platform (Meta Cloud API) is the upgrade path. It requires a Meta Business verification process and has its own per-message cost, but allows messages to be sent completely automatically, without a staff member needing to press "Send" in the WhatsApp app. This is not yet built — noted here purely as a possible future upgrade.

11. Security Notes

  • Passwords are never stored in plain text — Laravel hashes them automatically.
  • Login uses secure Bearer tokens (Sanctum) rather than storing a password on the device — a token can be revoked (logout) without changing the password.
  • Every business's data is isolated at the database-query level (Section 3.2) — this is enforced centrally, not something that can be forgotten in one particular screen.
  • Sensitive keys (Twilio credentials, Reverb secret, database password) live only in the server's .env file, which is never committed to source control.
  • Before going live: change all demo/seeded passwords, generate a fresh APP_KEY for production, and set APP_DEBUG=false so detailed error messages are never shown to real users.
  • The Super Admin's "permanently delete a business" action (Section 5.4) is irreversible and cannot be undone — it requires typing the exact business name to confirm, specifically to prevent an accidental click from wiping a real client's data.
